# Fantastat MongoDB Schema Contract

This document freezes the MongoDB schema consumed by the Fantastat web application.

The schema is generated by `builder.py` from the cache directory containing:

- `calendarYYYY.json`
- `quotazioniYYYY.csv`
- `statsYYYY.json`

The web application must treat this document as the stable backend contract.

## Collections

The builder writes six collections:

```text
calendars
calendar_matches
quotations
quotation_rows
players
teams
```

Three collections preserve the previous nested structure:

```text
calendars
quotations
players
```

Three collections are flattened for query performance and simpler web views:

```text
calendar_matches
quotation_rows
teams
```

## Collection: calendars

One document per season and matchday.

### Purpose

Used for matchday pages and grouped fixture views.

### Document shape

```json
{
  "_id": "2027:1",
  "year": 2027,
  "season": 2027,
  "giornata": 1,
  "matchday": 1,
  "matches": [
    {
      "year": 2027,
      "season": 2027,
      "giornata": 1,
      "matchday": 1,
      "match_text": "Internazionale - Torino",
      "team_home": "Internazionale",
      "team_away": "Torino",
      "home_team": "Internazionale",
      "away_team": "Torino",
      "score_home": 5,
      "score_away": 0,
      "match_date": "2025-08-25T18:45:00Z",
      "date": "2025-08-25T18:45:00Z",
      "stadium": "Giuseppe Meazza",
      "calendar_match_status": "FINISHED",
      "played": true,
      "raw_serie_a_match": {}
    }
  ]
}
```

### Required fields

```text
_id
year
season
giornata
matchday
matches
```

### Notes

- `giornata` and `matchday` are duplicated intentionally.
- `year` and `season` are duplicated intentionally.
- The web app should prefer `season` and `matchday`.
- `matches` preserves the original per-fixture calendar records.

The web app should use these aliases:

```text
name
team
role
quotation
initial_quotation
current_quotation
quotation_delta

```

It should not use the raw Fantacalcio names unless needed:

```text

squadra

QI

```

### Recommended query patterns

```python
db.quotation_rows.find({"season": 2027}).sort("FVM", -1)
db.quotation_rows.find({"season": 2027, "role": "A"})
db.quotation_rows.find({"season": 2027, "team": "INT"})
db.quotation_rows.find({"season": 2027, "name": {"$regex": "martinez", "$options": "i"}})
```

## Indexes

The builder creates these indexes after writing the collections.

### players

```python
database.players.create_index("player_id", sparse=True)
database.players.create_index("name")
database.players.create_index("team")
database.players.create_index("role")
```

### quotations

```python
database.quotations.create_index("year", unique=True)
database.quotations.create_index("season", unique=True)
```

### quotation_rows

```python
database.quotation_rows.create_index([("player_id", 1), ("season", 1)], unique=False, sparse=True)
database.quotation_rows.create_index([("season", 1), ("team", 1)])
database.quotation_rows.create_index([("season", 1), ("role", 1)])
database.quotation_rows.create_index([("season", 1), ("FVM", -1)])
database.quotation_rows.create_index([("season", 1), ("QA", -1)])
database.quotation_rows.create_index("name")
```

### calendars

```python
database.calendars.create_index([("season", 1), ("matchday", 1)], unique=True)
```

### calendar_matches

```python
database.calendar_matches.create_index([("season", 1), ("matchday", 1)])
database.calendar_matches.create_index([("season", 1), ("home_team", 1)])
database.calendar_matches.create_index([("season", 1), ("away_team", 1)])
```

### teams

```python
database.teams.create_index([("season", 1), ("team_code", 1)], unique=False)
```

## Current-season handling

The web app must not assume that all player records exist for the latest season.

For a season such as `2027`:

- `calendar_matches` can contain all 38 matchdays.
- `quotation_rows` can contain the current quotation snapshot.
- `players.seasons.2027.records` can be missing, partial or empty.

The web app must compute:

```json
{
  "season": 2027,
  "calendar_matchdays": [1, 2, 3, 4, 5],
  "available_player_matchdays": [1, 2],
  "last_known_matchday": 2,
  "is_current_or_partial": true
}
```

The frontend must display unavailable future matchdays as fixtures, not as missing data errors.

## Backend rule

The web application must use this precedence:

1. `quotation_rows` for dashboard, search, filters and rankings.
2. `players` for player pages, player summaries and timelines.
3. `calendar_matches` for team fixtures, matchdays and future schedule.
4. `teams` for filter options.
5. `quotations` and `calendars` only when the nested full-season document is useful.
